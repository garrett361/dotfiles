# Running a perf investigation with subagents

Lessons from coordinating implementation, correctness, tuning and timing subagents on one shared GPU cluster (a night-long Hopper kernel port, 8x H200 nodes). Read this before fanning out work that both edits code and measures it.

## Before any agent starts

- Record the environment once and hand it to every agent in one shared brief file: partition time limits (`scontrol show partition <p>`), driver and CUDA version on a compute node (login hosts may have no GPU or `nvidia-smi`), interpreter path, and which existing tests already fail on this hardware at the base commit. Without the baseline failure list, agents misattribute pre-existing failures to their change or waste time on them.
- Measure the hardware's reference points up front and put them in the brief: power-cap behavior (`tools/do-bench.md`, power cap), peer copy bandwidth per direction, and the vendor-library roofline for the op (for example `torch._grouped_mm` for grouped GEMMs). Every later number is read against these.
- Write the shared brief as a file (rules, how to run on GPUs, which GPUs each agent owns, ownership of files, report format) and point each agent prompt at it; prompts then carry only the task. Pair it with one brief file per agent that lists the files that agent owns, the frozen arms it times, and where its report and interim progress file go. In a night-long run of about 25 agents this layout (shared brief, per-agent briefs, frozen arms, one timing agent on a dedicated node, progress files, one findings file) let agents run concurrently in one worktree without conflicting edits; interim progress files showed where each long-running agent stood without interrupting it.
- Verify every hazard claim in the plan with an independent reproduction before an agent codes a guard for it. A claimed buffer overlap that a plan asked to guard against turned out unreachable: the configuration's validation forced the sizes to multiples of the alignment. One focused reproduction agent (a mirror of the arithmetic plus real configurations, under 2 minutes of GPU) settled it.
- Decide how the result will be judged before the timing agents start: the decision metric (raw ms, same node, same session, ABBA arm order), and, for communication fused or overlapped into compute, a per-launch decomposition (`tools/exposed-comm.md`) rather than end-to-end time alone. Under a power cap the fused arm runs at a lower clock by construction, so matched clocks cannot be the criterion (`tools/do-bench.md`, power cap).

## Allocations and GPUs

- Hold one allocation without a shell (`salloc ... --no-shell`) and have every agent run steps in it with `srun --jobid=<job> --overlap`, each pinned to its own `CUDA_VISIBLE_DEVICES` and its own `TRITON_CACHE_DIR`.
- Hold a second, dedicated node for timing only, for the whole investigation, and give it to one timing agent at a time. A shared development node gave 2 to 25% spread per arm; the dedicated node gave under 0.5% drift across sessions. When its time limit expires, re-allocate the same node with `--nodelist`.

## Code ownership and freezing

- Implementation agents in one worktree must not commit, stash or reset; each owns a disjoint file set and lists every file it changed. The coordinator reviews and commits in conventional-commit chunks, so every timing arm maps to a commit.
- Freeze each arm for timing with `git archive <sha> | tar -x -C <dir>` and run it via `PYTHONPATH=<dir>` with the project's interpreter (an editable install is shadowed by `PYTHONPATH`); have the agent record `module.__file__` per arm. This avoids extra worktrees and lets tuning continue in the live tree while the frozen arm is timed.
- Run frozen arms with the working directory outside the project checkout: `python -c` and `python -m` put the working directory first on `sys.path`, ahead of `PYTHONPATH`, so launched from the checkout they silently import the live tree instead of the frozen copy. The recorded `module.__file__` catches this.
- To load two versions of a package in one process (e.g. to compile the baseline kernel next to the new one and diff their PTX), rename the archived copy's top-level package directory (e.g. `pkg_base`); this works when the package's internal imports are relative.
- A test that compares built artifacts to the working tree races with any agent editing the tree; run it when no one is editing.

## What to ask of timing and tuning agents

- Timing agents: reuse the previous agent's cases files and flags verbatim (from `commands.sh`), rerun the previous arm in the same session to control for drift, log clocks, and append a new section to `NOTES.md` instead of rewriting.
- Prototype agents (a new producer, a new kernel design): require the arithmetic floor (bytes over link rate, per-SM rate times the SMs spared, co-resident SMs left) and a measurement of the critical path alone before any full build, and a verdict with evidence; see `../kernels/SKILL.md`. A multicast prototype settled a no-go this way in about an hour.
- Tuning agents: time-box them, require a log of everything tried (including failures and why), keep a static config table, require determinism and bitwise equality with the reference where it held before, and treat their development-node numbers as candidates only; confirm on the timing node before claiming a result.
- Ask every agent for reusable findings in its report and append them to one findings file as reports arrive; fold that file into this skill at the end rather than editing the skill from several agents at once.
- Correctness or stress agents: start a stress run (hundreds of steps per seed, routing or inputs re-drawn every step, several seeds, every arm checked bitwise against the reference each step) as soon as the feature is wired, not after tuning. Rare hangs need many runs: two intermittent hangs appeared in 20 runs of 200 to 300 steps (about 2 per 28k calls, estimated), and a 20-run control without the feature was too short to tell the causes apart.

## Harness pitfalls seen in agent runs

- Never `source` an investigation's `commands.sh` to get helper functions: it reruns every recorded command (an agent regenerated and partly overwrote earlier baseline outputs this way). Keep helpers in a separate file that `commands.sh` sources, or extract only the helper block with `sed -n`.
- In `srun ... bash -c 'cd X && export P=... && cmd & PID=$!'` the `&` backgrounds the whole `&&` list, so the `export` never reaches the foreground command. Background only the logger: `cd X && export P=... && { nvidia-smi ... > log & } && cmd`.
- In multi-rank scripts, print the traceback before calling `destroy_process_group` (e.g. in an `except` that prints, then the `finally` that tears down). When one rank raises while its peers block in device-side barriers, `destroy_process_group` hangs on that rank and the exception is never printed; only a faulthandler dump showed the rank sitting in teardown.
- To locate a multi-rank hang to an arm and a rank: print a start line per arm and step, arm `faulthandler.dump_traceback_later(<secs>, repeat=True)` on every rank, and capture `nvidia-smi` utilization while it hangs. The idle GPU (0%) is the rank that failed; 100% on the others means they are spinning in device barriers.
- Per-step printing from every rank through `srun` ties rank progress to the login host's output pipe: when the reader stalls (a slow or nearly full network volume), every rank blocks on its next write. Pausing the reader for 120 s stalled an 8-rank job for 88 s and dropped lines (`srun` printed "Abandoning IO"), the same signature as a suspected device hang. Write per-rank heartbeats and tracebacks to files on the node, and write the traceback before any collective or teardown, then `os._exit(1)`, so a failing stderr cannot swallow it.
- `py-spy` may be unable to attach on cluster nodes (ptrace denied); register `faulthandler.register(signal.SIGUSR1, file=<per-rank file>)` and send `SIGUSR1` instead.
- Before chasing a rare hang, estimate whether the follow-up has the power to see it: at a reported 2 hangs in 20 runs, 0 hangs in 118 runs of the same configuration has probability about 2e-5, so the original runs differed in some condition (environment, harness, output path) rather than being unlucky. Report hang rates with call counts.
- Give every run in a seed loop its own log name (seed, arm set, attempt). A rerun of a failed seed overwrote the only log of the failure.
- Tests marked as needing N GPUs fail with "invalid device ordinal" when fewer are visible. That reads like a code failure but is the allocation; rerun on N GPUs before investigating.
- When a launcher (a trainer CLI, a job wrapper) starts the worker processes, confirm env-based arm selection reached them: read `/proc/<pid>/environ` of a worker during the run. One trainer prepended its own `PYTHONPATH` entry ahead of the caller's, so check the worker's `module.__file__` as well.
- To test call-site wiring before the callee's new keyword arguments exist (one agent edits the launcher while another adds the kernel arguments), put a throwaway `sitecustomize.py` on `PYTHONPATH`, outside the repo, that wraps the callee and drops the not-yet-supported keyword arguments when they are `None`. Unlike a pytest plugin, it also loads in `torch.multiprocessing.spawn` children. Rerun without it once the callee lands.
